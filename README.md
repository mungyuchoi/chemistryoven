## 1️⃣ 개발 환경 셋팅 (30분)

> 🎯 이 파트의 목표: **"A의 폰에서 케미스트리오븐 앱이 뜨는 순간"** 을 만든다.

### 1-1. Android Studio 설치 (10분)

- 💬 말하기 포인트: *"이건 앱을 폰에 넣어주는 공장이라고 생각하면 돼. 직접 쓸 일은 거의 없어."*

### 1-2. Flutter SDK 설치 (5분)

- 💬 말하기 포인트: *"flutter doctor는 건강검진이야. 빨간 X가 있으면 나한테 스크린샷 보내."*

### 1-3. Git 설치 + GitHub 가입 (5분)

- GitHub 가입 → 내가 보낸 **Collaborator 초대 수락**

### 1-4. 프로젝트 가져오기 (git clone) (3분)

## 2️⃣ 클로드 코드 & 바이브코딩 핵심 워크플로우 (30분)

> 🎯 이 파트의 목표: **"1 세션 = 1 기능 = 1 커밋+푸시"** 습관을 몸에 새긴다.

### 2-1. Claude Code 설치 (5분)
- Node.js 설치 (LTS 버전) → 터미널에서:
```bash
npm install -g @anthropic-ai/claude-code
```
- 프로젝트 폴더에서 `claude` 실행 → 로그인
- 💬 최신 설치법이 바뀔 수 있으니 공식 문서 링크도 함께 전달: https://docs.claude.com/en/docs/claude-code/overview

### 2-2. 프로젝트 열기 (3분)
- 반드시 **프로젝트 루트 폴더에서** `claude` 실행
- 첫 실행 시 `/init` 으로 CLAUDE.md 생성 → 프로젝트 규칙을 여기에 적어둘 수 있다고 소개
- 💬 강사 팁: CLAUDE.md에 미리 아키텍처 설명, 폴더 구조, 코딩 규칙을 적어두면 A의 바이브코딩 품질이 크게 올라감 (**강의 전 미리 작성 추천**)

### 2-3. 핵심 원칙: "1 세션 = 1 기능" (5분)
- 하나의 세션에서는 **하나의 기능만** 구현한다
- 서로 영향 없는 화면/기능이라면 **2~3개 세션을 동시에** 열어도 OK
  - 예: 세션1 = 프로필 화면 수정 / 세션2 = 레시피 목록 정렬 기능
  - ⚠️ 단, **같은 파일을 건드리는 기능은 절대 동시 진행 금지** (충돌 발생)
- 💬 비유: *"요리사 2명이 각자 다른 도마에서 일하면 괜찮은데, 같은 도마를 쓰면 사고 나."*

### 2-4. 기능 구현 → 검증 → 커밋 → 푸시 루틴 (10분)

**A에게 각인시킬 4단계 루틴:**

```
① 구현   : "레시피 즐겨찾기 기능 만들어줘. 하트 아이콘 누르면 Firestore에 저장돼야 해"
② 검증   : flutter run (또는 핫리로드)으로 폰에서 직접 확인
③ 커밋   : 기능이 동작하면 → 모델을 낮춰서(/model) 커밋 요청
           "지금까지 작업 커밋해줘. 커밋 메시지는 한글로 간단히"
④ 푸시   : "푸시까지 해줘"
```

- 💰 **비용 절약 팁**: 커밋/푸시 같은 단순 작업은 `/model` 명령으로 **낮은 모델로 전환** 후 진행 → 고성능 모델은 기능 구현에만 사용
- ⚠️ **절대 규칙**: *"기능이 끝났는데 커밋을 안 하는 건, 게임에서 보스 잡고 저장 안 하는 거랑 같아."*

### 2-5. 실습: 실제 기능 하나 같이 구현해보기 (7분)
- 간단한 기능 하나를 A가 직접 프롬프트 입력하게 시키기
  - 추천 예시: "설정 화면에 앱 버전 표시해줘" (리스크 낮고 성공 확률 높음)
- 구현 → 폰 확인 → 커밋 → 푸시까지 **A 손으로 완주**시키기

## 3️⃣ 버전 관리 & 배포 프로세스 (15분)

> 🎯 이 파트의 목표: 역할 분담을 명확히 한다. **"버전 올리고 푸시하면, 나머지는 내가 한다."**

### 3-1. 버전 읽는 법 (5분)
- `pubspec.yaml` 파일 열어서 보여주기:
```yaml
version: 1.0.1+2
         │ │ │  └─ 빌드번호(+2): 스토어 업로드마다 무조건 +1 (내부용 일련번호)
         │ │ └─── 패치: 버그 수정
         │ └───── 마이너: 기능 추가
         └─────── 메이저: 대규모 개편
```
- 💬 규칙 단순화: *"테스트 버전 올리고 싶으면 → `1.0.1+2`를 `1.0.2+3`으로 바꾸고 커밋+푸시. 둘 다 올리는 것만 기억해."*

### 3-2. 배포 파이프라인 — 역할 분담 (5분)

```
[A]  기능 구현 → 커밋/푸시 → 버전업(1.0.2+3) → 커밋/푸시 → 나에게 "배포 요청" 연락
[나] git pull → AAB 빌드 → Play Console 업로드 → 내부 테스트 트랙 배포
[A]  내부 테스트 링크로 설치 → 지인들과 테스트
```

### 3-3. Play Console — A가 직접 할 일 (5분)
- 내가 보낸 **Play Console 초대 수락** 확인
- A가 직접 채워야 할 것 (오너십 부여):
  - [ ] 앱 설명 (짧은 설명 / 자세한 설명)
  - [ ] 스크린샷 (폰 최소 2장 이상)
  - [ ] 그래픽 이미지 (1024×500)
  - [ ] 앱 아이콘 (512×512)
  - [ ] 카테고리, 콘텐츠 등급 설문
  - [ ] 개인정보처리방침 URL
- 💬 말하기 포인트: *"스토어 페이지는 네 앱의 얼굴이야. 이건 개발이 아니라 마케팅이라 네가 제일 잘해."*
- 꿀팁: 스크린샷/설명도 클로드에게 시켜서 만들 수 있다고 알려주기

## 4️⃣ Firebase 기본 개념 — 초보자용 비유 설명 (20분)

> 🎯 이 파트의 목표: 코드가 아니라 **개념 지도**를 심어준다. "데이터가 어디에 어떻게 저장되는지"만 알면 바이브코딩 프롬프트 품질이 올라간다.

### 4-1. Firestore = 앱의 데이터베이스 (7분)
- 💬 비유: *"엑셀 파일들이 모여있는 폴더라고 생각해."*
  - **컬렉션** = 엑셀 파일 (예: `users`, `recipes`)
  - **문서** = 엑셀의 한 행 (예: 사용자 1명, 레시피 1개)
  - **필드** = 엑셀의 한 칸 (예: 이름, 이메일, 생성일)
- Firebase 콘솔 직접 열어서 실제 데이터 구경시키기 (백문이 불여일견)
- 이미 구축된 구조 소개: `users/{uid}` 아래에 사용자 정보, `fcmToken`도 여기 저장됨
- 프롬프트 팁 전수: *"클로드한테 시킬 때 '이 데이터는 Firestore의 recipes 컬렉션에 저장해줘'처럼 위치를 말해주면 훨씬 정확해져."*

### 4-2. Storage = 파일 창고 (3분)
- 💬 비유: *"Firestore가 엑셀이면, Storage는 사진/파일을 넣는 클라우드 창고야."*
- 이미지 업로드 흐름: 폰에서 사진 선택 → Storage에 업로드 → 그 주소(URL)를 Firestore에 기록

### 4-3. Cloud Functions = 자동으로 일하는 서버 직원 (5분)
- 💬 비유: *"앱이 잠들어 있어도 24시간 일하는 알바생. 특정 사건이 일어나면 자동으로 움직여."*
  - 예: 새 댓글이 달리면 → 자동으로 글 작성자에게 푸시 알림 발송
  - 예: 매일 밤 12시에 → 오래된 데이터 자동 정리
- ⚠️ 안내: Functions 배포는 당분간 나(개발자)가 담당. A는 "이런 자동화가 필요해"라고 요구사항만 정리하면 됨

### 4-4. Authentication + 카카오 로그인 (3분)
- 이미 구축 완료 상태이므로 개념만:
  - 💬 비유: *"앱의 출입문 경비원. 카카오 로그인은 '카카오가 신원보증 해주는 패스트트랙'이야."*
- `uid` 개념만 확실히: *"로그인하면 사용자마다 고유번호(uid)가 생기고, 모든 데이터는 이 번호에 연결돼."*

### 4-5. FCM (푸시 알림) (2분)
- 이미 `users/{uid}/fcmToken`으로 저장되도록 구축 완료
- 💬 비유: *"fcmToken은 각 폰의 우편함 주소야. 알림 보내려면 이 주소로 보내는 거야."*

## 5️⃣ Admin SDK & env 폴더 셋팅 (10분)

> 🎯 이 파트의 목표: 클로드 코드가 Firestore/Storage에 **직접 접근**할 수 있게 해서, A가 데이터 조회/수정도 바이브코딩으로 하게 만든다. 단, **보안 규칙은 목숨처럼.**

### 5-1. 셋팅 순서 (같이 진행)
1. 프로젝트 루트에 `env/` 폴더 생성
2. Firebase 콘솔 → ⚙️ 프로젝트 설정 → **서비스 계정** 탭 → **새 비공개 키 생성** → JSON 다운로드
3. 다운받은 JSON을 `env/` 폴더에 넣기 (예: `env/firebase-admin.json`)
4. `.gitignore`에 `env/` 포함 확인 (이미 넣어뒀다면 같이 열어서 확인시키기)

### 5-2. ⚠️ 보안 각인 (반드시 강조)
- 💬 말하기 포인트: *"이 JSON 파일은 **우리 앱 금고의 마스터키**야. 이게 유출되면 누구든 우리 DB를 통째로 지울 수 있어."*
- **3대 금지사항:**
  1. 카톡/이메일/슬랙으로 이 파일 전송 금지
  2. env 폴더를 .gitignore에서 빼는 것 금지
  3. 클로드가 "이 파일을 코드에 복사할게요" 하면 **중단시키기**
- git에 안 올라가는지 검증: `git status` 쳤을 때 env/가 안 보이면 정상

### 5-3. 활용 예시 보여주기
- 클로드 코드에 이렇게 시킬 수 있다고 시연:
  - *"env/firebase-admin.json 이용해서 recipes 컬렉션에 있는 문서 개수 세줘"*
  - *"테스트 유저 3명 데이터를 Firestore에 넣어줘"*
- 💬 말하기 포인트: *"이제 너는 데이터 확인하려고 나한테 물어볼 필요 없이, 직접 조회하고 수정까지 할 수 있어."*

강의 1회차에 다 넣지 말고, **2회차 or 필요 시점에** 진행 추천:

| **Firestore 보안 규칙 개념** | A가 기능 추가하다 규칙 때문에 permission-denied 에러를 반드시 만나게 됨. "규칙 = 금고 자물쇠, 함부로 풀면 안 됨. 에러나면 나한테 문의" 정도만 1회차에 언급 | 2회차 |
| **Firebase 요금 구조 + 예산 알림** | 무한루프 코드가 Firestore 읽기 폭탄 → 과금 사고 방지. 예산 알림 미리 설정해두기 (이건 강사가 직접) | 강의 전 강사가 셋팅 |

| **테스트 계정 분리** | 실데이터 오염 방지. 테스트용 카카오 계정 하나 만들기 | 2회차 |
